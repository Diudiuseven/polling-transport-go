# polling-transport-go

面向变更订阅的统一传输层。客户端可以通过**轮询（poll）**、**长轮询（long-poll）**
和**长连接事件流（stream）**三种方式订阅同一份有序变更序列，并在断线或慢消费之后
仍按游标正确续传。

## 特性

- **单一有序变更源**：三种传输方式从同一个 gap-free 的连续前缀读取变更，
  任一时刻各订阅者看到的游标视图完全一致，不同方式之间没有可见的语义偏差。
- **按游标续传（不丢、不重、连续）**：客户端携带自己**真正处理成功**的位置
  重连即可。重连起点一律为 `max(客户端传入游标, 服务端已确认位点)`，三种方式
  完全一致；慢订阅者断线或被判定落后时，已投递但未读/未确认的积压变更会从日志
  重新投递，已确认的变更绝不重复，因此客户端看到的序列不会出现空洞。
- **乱序与重复归一化**：变更携带单调递增的序号，乱序到达先入缓冲区、补齐空洞后
  再推进；重复序号直接丢弃。
- **长轮询挂起而非空转**：无新变更时长轮询挂起等待，有新变更或超时上限时立即
  返回。日志前沿通过**广播代次通道（generation channel）**唤醒所有等待者，
  每次追加的唤醒开销为 O(1)，与挂起请求数量无关。
- **慢订阅者背压**：每个订阅者拥有独立的有界缓冲；单个订阅者变慢只阻塞自己，
  不影响其他订阅者。缓冲发送阻塞超过写超时上限时，该连接收到
  `EventResync` 标记并关闭，客户端用真实处理位置重连即可从日志补齐，
  重新同步只终止连接、绝不跳过任何变更。
- **订阅生命周期与容量不泄漏**：`MaxSubscriptions` 只约束**当前真实活跃**的
  连接（在线事件流、处理中/挂起中的轮询与长轮询）。一次性请求返回即释放名额，
  长期高并发运行下占用稳定在真实活跃订阅数量附近，不随累计请求数无界增长；
  真实打满时上限仍然生效。
- **优雅关闭与排水**：关闭时所有挂起的长轮询被唤醒（`ErrShutdown`），事件流收到
  终止事件（`EventClosed`），后台任务全部退出，无 goroutine 或连接泄漏。
- **并发安全**：所有共享状态在多订阅者并发访问下安全，通过 `-race` 检测。
- **可测试时钟**：内置真实时钟与内存假时钟（`FakeClock`），长轮询超时、心跳、
  背压等时间相关测试可确定性重复。

## 核心概念

### 变更日志（ChangeLog）

```go
type Change struct {
    Seq   int64  // 全局单调递增序号
    Key   string
    Value []byte
    Time  time.Time
}
```

- `Append` 接收变更：序号已存在则丢弃（去重）；序号按 `1,2,3...` 连续排列，
  乱序到达时先缓存，空洞补齐后前沿（frontier）推进。
- `Read(afterSeq, limit)` 只返回序号严格大于 `afterSeq` 的连续前缀中的变更，
  因此读者永远看不到空洞。
- `WaitChan(afterSeq)` 返回一个通道：当前沿已超过 `afterSeq` 时立即关闭，否则
  在前沿推进时关闭。所有等待者共享同一个广播通道，单次关闭唤醒全部。

### 三种传输

| 方式 | 接口 | 语义 |
| --- | --- | --- |
| 轮询 | `Poll(ctx, id, afterSeq, limit)` | 立即返回当前可用变更，无变更时返回空 |
| 长轮询 | `LongPoll(ctx, id, afterSeq, limit, timeout)` | 有变更立即返回；否则挂起直到有变更或超时，超时返回空 |
| 事件流 | `Stream(ctx, id, afterSeq)` | 返回 `<-chan Event`，持续推送变更，空闲时发心跳 |

三种方式返回的变更顺序、游标含义完全相同：`next` 为本次最后一条变更的序号，
客户端下次请求携带该游标。

### 游标一致性与续传

- 游标 = 客户端已**真正处理成功**的最后一条变更序号。服务端只投递序号严格大于
  游标的变更。
- 无论使用轮询、长轮询还是事件流，重连/重新发起订阅时的起点一律为：

  ```
  start = max(客户端传入 afterSeq, 服务端记住的已确认位点 acked)
  ```

- 因此两种位置都安全：
  - 携带**最后处理成功的位置**：从该位置之后第一条变更开始连续投递；
  - 携带**更早的位置**（过期游标）：未确认的部分会被重新投递（断线续传为
    at-least-once），但**已确认的变更不会重复**。
- 关键点：**“已投递”不等于“已确认”**。事件流把事件压入客户端缓冲后就会推进
  该连接内部的投递游标，但该游标只属于当前这一代连接，重连时会重置，绝不会用来
  跳过变更。慢订阅者积压了一批尚未取走的变更时断线，或被判定落后重新同步，这批
  变更仍然保留在变更日志中，会从 `start` 之后被重新投递，客户端序列不会出现空洞。
- 客户端应对跨连接可能的重复投递按 `Seq` 去重；同一条连接内每条变更只投递一次。
- 事件流通过 `Ack(ctx, id, seq)` 确认已处理位置；确认位点是所有后续续传的下界。
  日志保留全部历史变更，按游标重连可以从任意位置恢复。

### 背压、积压与重新同步

- 每个事件流订阅者有一个容量为 `BufferSize` 的有界缓冲通道。
- 泵（pump）向通道发送事件：缓冲满时阻塞（只对该订阅者施加背压，不影响他人）。
  阻塞超过写超时（`LongPollTimeout`）时，泵排空缓冲、发送 `EventResync` 标记并
  关闭该连接，同时释放订阅名额。
- **重新同步的边界**：resync 只终止连接，既不移动确认位点，也不截断或跳过任何
  变更。被排空丢弃的缓冲事件仍在日志中。客户端收到 `EventResync`（或发现连接
  断开）后，用自己**真实处理成功**的游标重新调用 `Stream`，服务端从
  `max(该游标, acked)` 之后开始连续投递，积压全部补齐、不重确认、不留空洞。
- 轮询与长轮询没有服务端缓冲积压：一次请求返回的批次若客户端只处理了一部分，
  下次请求携带真实处理位置即可，语义与事件流完全相同。

### 订阅生命周期与容量

- `MaxSubscriptions` 统计的是**当前活跃连接名额**，包括：在线的事件流、正在处理
  的轮询、以及挂起中的长轮询。
- **一次性请求（轮询/长轮询）只在请求执行期间占用名额，返回时一定释放**。因此
  即使服务长期处理海量带新 id 的一次性请求，名额占用也会稳定在真实活跃订阅数量
  附近，不会随累计请求数无界增长。
- 当名额被真实活跃连接占满时，新订阅仍会被拒绝（`ErrTooManySubscriptions`），
  上限照常生效；活跃连接结束（流关闭、退订、请求返回）后名额立即归还。
- 同一 `id` 的新请求会**取代**上一代连接：旧的事件流泵或挂起的长轮询被取消，
  名额移交给新一代，不会关闭新连接的通道，也不会泄漏 goroutine。
- 已退订（`Unsubscribe`）的 id 会同时清除连接名额与续传进度。

### 优雅关闭

```go
err := server.Shutdown(ctx)
```

- 关闭后新请求返回 `ErrShutdown`。
- 挂起中的长轮询立即返回 `ErrShutdown`。
- 打开中的事件流收到 `EventClosed` 后关闭。
- 所有后台 goroutine 退出后 `Shutdown` 返回（或 ctx 超时）。

## 配置

```go
type Config struct {
    PollInterval      time.Duration // 轮询间隔建议值，必须 > 0
    LongPollTimeout   time.Duration // 长轮询最大挂起时间，必须 > 0
    BufferSize        int           // 单订阅者缓冲上限，必须 > 0
    MaxSubscriptions  int           // 最大并发订阅数，必须 > 0
    HeartbeatInterval time.Duration // 事件流空闲心跳间隔，必须 > 0
}
```

使用 `DefaultConfig()` 获取默认配置；`New` 会调用 `Validate`，非法配置返回
`ErrInvalidConfig` 及可读错误信息。额外约束：`HeartbeatInterval` 不应超过
`LongPollTimeout`。

## 测试

```bash
go test ./... -race
go test -race -count=10 ./...   # 重复运行，验证稳定性与无数据竞争
```

- `log_test.go`：追加、去重、乱序归一、空洞补齐唤醒、游标读取。
- `server_test.go`：轮询、长轮询（立即返回/挂起/超时/关闭唤醒）、事件流、
  心跳、背压与重新同步、断线重连、已确认位点不重复、最大订阅数、配置校验、
  优雅关闭排水、多订阅者并发、100 个长轮询同时唤醒。
- `resume_test.go`（续传不丢不重，三种方式一致）：
  - 慢事件流订阅者在积压尚未读完时断线，分别携带精确位点、更早日位点、中间位点
    重连，验证从该位置之后第一条开始连续投递、无空洞；
  - 写超时触发 `EventResync` 后用真实位点重连，验证缓冲中被丢弃的事件从日志
    完整补齐；
  - 轮询/长轮询在拿到大批变更只处理一部分后，用真实位点续传，以及 ack 之后用
    过期游标不重复。
- `capacity_test.go`（容量不泄漏）：数千个带唯一 id 的一次性轮询/长轮询之后
  活跃名额回落、新订阅仍可建立；挂起中的长轮询在其存活期间仍受上限约束；续传
  进度表在内存时钟越过空闲期后被清扫。
- `concurrent_test.go`：三种传输方式的大量订阅者并发消费、变更并发追加，
  其中事件流订阅者分别模拟慢消费与频繁断线重连，验证每人收到的序列严格连续、
  无空洞无重复，关闭后无残留名额与 goroutine。

时间相关测试使用 `FakeClock`（内存时钟）：只有调用 `Advance` 才会推进时间，
因此长轮询超时、心跳、写超时、空闲清扫等行为可确定性复现，不依赖真实时间。

### 手工验证两类问题

- **慢订阅者断线续传**：运行
  `go test -race -run TestResume_Stream_SlowSubscriberBacklogReconnect -v`。
  该测试先让缓冲仅为 2 的订阅者只处理前 3 条、再积压到第 12 条，随后模拟断线
  并携带真实位点重连，断言收到 `4..12` 连续且仅一次。
- **容量不泄漏**：运行
  `go test -race -run TestCapacity_OneShotRequestsReleaseSlots -v`。
  该测试在上限为 16 的服务上执行 4000 个一次性请求（2000 轮询 + 2000 长轮询），
  断言活跃名额始终只剩 1 个真实长连接，并可继续建立新订阅。

## 接口速览

```go
cfg := transport.DefaultConfig()
srv, err := transport.New(cfg)

// 追加变更
srv.Log().Append(transport.Change{Seq: 1, Key: "order", Value: []byte("...")})

// 轮询
changes, next, err := srv.Poll(ctx, "poller-1", cursor, 100)

// 长轮询
changes, next, err := srv.LongPoll(ctx, "lp-1", cursor, 100, 30*time.Second)

// 事件流
ch, err := srv.Stream(ctx, "stream-1", cursor)
for ev := range ch {
    switch ev.Type {
    case transport.EventChange:
        // 处理 ev.Change
        srv.Ack(ctx, "stream-1", ev.Cursor)
    case transport.EventHeartbeat:
        // 心跳
    case transport.EventResync:
        // 用最后游标重连
    case transport.EventClosed:
        // 服务端关闭
    }
}

// 退订 / 关闭
srv.Unsubscribe(ctx, "stream-1")
srv.Shutdown(ctx)
```
